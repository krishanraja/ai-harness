# Capture proposal, 2026-09-12

## Hosted observation capture

Named asker and owner: Krish, in the 2026-09-12 harness audit and implementation
thread. He asked that the repository automatically learn from real-world work,
problems, and patterns, then explicitly approved the hosted alternative and
said to proceed across this machine and the intermittently connected second
machine.

Written ask (Krish, 2026-09-12): "we need to somehow ensure that this repo
automatically learns from real world work I do, problems encountered, patterns
observed etc."

Ruling (Krish, 2026-09-12): This personally commissioned harness infrastructure
is explicitly asked for and is not subject to the paying-leader product-demand
test.

Ruling (Krish, 2026-09-12): The narrow redacted
`record_harness_observation` write is standing-approved without per-event
confirmation; no other outbound write or payload expansion is approved.

Krish approved replacing machine-local learning scripts with one hosted,
stateless MCP emitter. The same approval explicitly includes the intermittently
connected second workstation, but the architecture must not depend on that
machine or its mapped drive being online.

The accepted rule records only small, redacted signals after explicit
corrections or material reusable outcomes. It rejects routine-success noise,
raw conversations, sensitive data, machine identity, and direct canon edits.
Tool absence or failure is non-blocking and cannot create a local shadow
ledger. Evidence can reach canon only through human review, regression, and a
governed release.

This approval is also the standing authority for the narrow external write
performed by `record_harness_observation`. It does not authorize any other
outbound action or any wider payload. `ctrl-capture` remains the only owner that
may cluster, interpret, and propose promotion of the resulting evidence. The
scheduled importer batches signals automatically so the design does not create
a review obligation for every event.

The alternative was one watcher or scheduled script per workstation, with n8n
as an optional relay. It was rejected because it creates configuration drift,
availability coupling, more credential copies, and silent gaps whenever a
machine or mapped drive is offline.

Validation requires one tool only, separately revocable client identities,
server-owned surface attribution, deterministic retry behavior, strict
redaction, a per-client safety limit, cross-adapter render parity, and held-out
cases for positive capture, routine-success refusal, and honest tool failure.
