## Block 1: description length with trailing exclusions (36 occurrences)

Layer: **3, a routing fix** (description structure), conditional on an owner answer.

EVIDENCE
- 6 skills, each observed on 5 to 6 days: `build-apps-with-krish` (989 characters), `ctrl-intake` (941), `krish-voice` (939), `verification-loop` (1004), `ux-testing-agent` (981), `krish-build` (940). Quoted: "carries negative trigger conditions, on a client that reports shortening descriptions to fit a context budget. Exclusions sit at the end of a description and are what a truncation removes first."
- Unique skills: 6. Lengths are constant across days, so this is one standing condition per skill, not 36 events.
- Opportunity denominator: AWAITING. The brief does not name the client, its budget in characters, or any instance of an actual truncation.
- Related prior evidence: `docs/proposals/2026-10-06-canary-routing-repair.md` already moved the strategy precondition to the front of `krish-build` metadata.

ALTERNATIVE EXPLANATIONS
- The audit threshold may be conservative and the client budget may comfortably fit about 1000 characters. No truncation has been observed, only a risk.
- Exclusions at the end may be the load-bearing disambiguation that canaries currently pass on; moving them could regress positive triggers.
- The reported shortening may apply to a client the harness does not target for these skills.

PROPOSED CHANGE
- Owner question first: which client reports the budget, what is the figure, and is any of the six actually shortened there?
- If a truncation is confirmed, restructure each affected description so the exclusion clause is stated in the first sentence or two, keeping total length at or under the confirmed budget. No new trigger phrases, no scope change. Route through `ctrl-build` positive, negative and adversarial collision evaluation and the full regression before any release.
- If no truncation is confirmed, the audit line is a warning and nothing changes.

IF WRONG
- Moving exclusions forward can disturb neighbour routing (for example `krish-build` against `strategy-brief`), and a skill could begin firing where it should not. Canary owners notice first, via a new over-trigger line in the brief.

VALIDATION
- Before release: a client-side readback of the shortened description text for each of the six skills, which shows whether exclusions survive. Then the existing trigger eval cases for the six skills and their neighbours, plus one new negative case per skill whose result depends on the exclusion clause surviving. Gate 10 requires the regression case before release.

SIZE / CONTEXT DELTA: expected to reduce or hold description length; before values above, target AWAITING the budget figure.

PRIOR KNOWN-GOOD + ROLLBACK: current `SKILL.md` front matter of each of the six at `main`; revert the single commit per skill.
